Investor portal safeguard. A fixed 21% annual return is a financial obligation, not a marketing line. Before the portal accepts any money, an Indian lawyer and a chartered accountant should confirm the legal structure, the deposit and securities rules, the tax treatment and the disclosures. The architecture keeps the portal read-only (calculator plus statements) until that sign-off, and no wording says “guaranteed”.
Compliance before launch. Check the Rent-a-Motorcycle Scheme licence, vehicle permits, commercial insurance and tax requirements with the Uttarakhand transport authority. Architecture layout

System architecture

The API is a modular monolith: one Express deployable with clear domain modules, plus a background worker that runs from the same codebase. A 30-vehicle business doesn't need microservices. If any module ever outgrows the monolith, its boundary is already clean enough to split it out.

Why this shape

Next.js renders, Express decides

Next.js handles SEO pages, layouts and UI only. Every business rule (price, availability, refunds, investor maths) runs in Express. The mobile app and the website then always show the same numbers.

PostgreSQL blocks double bookings

An EXCLUDE USING gist constraint on (vehicle_id, booking period) rejects overlapping active bookings at the database level, even if two requests arrive in the same millisecond.

Work that can wait goes to a queue

Releasing unpaid holds after 15 minutes, WhatsApp confirmations, return reminders, invoice PDFs and repayment-due alerts run in a BullMQ worker, so API responses stay fast.

One shared package

packages/shared holds the Zod schemas, enums and pricing formula. The web app, API and mobile app import the same code, so validation never drifts apart.

Booking sequence (happy path)

  1. The customer picks a location and dates. Next.js calls GET /availability, and the API returns models with free-unit counts and a priced quote.
  2. The customer taps Book. POST /bookings opens a DB transaction, locks one free vehicle with FOR UPDATE SKIP LOCKED, and inserts the booking as PENDING_PAYMENT with a 15-minute hold.
  3. The API creates a Razorpay order (rental + deposit) with an idempotency key and returns the order_id to the client.
  4. The customer pays through Razorpay Checkout (UPI or card). Razorpay sends a payment.captured webhook, which the API verifies with an HMAC signature.
  5. The booking moves to CONFIRMED, a payment row is written, and the worker sends the WhatsApp confirmation and invoice PDF.
  6. At pickup, staff run the digital handover (licence check, photos, odometer, e-signed agreement), and the booking becomes ONGOING.
  7. At return: inspection, extra-km and late fees, then COMPLETED and the deposit refund through the Razorpay refund API.

Engineering rules

  • Money is stored as integer paise (BIGINT). No floats in the database. ₹649 is stored as 64900.
  • Times are timestamptz in UTC and shown in Asia/Kolkata in the UI.
  • Every write that moves money takes an Idempotency-Key header and is logged in audit_logs.
  • Schema changes only through migrations. Never run sequelize.sync() in production.
  • Controllers never import models. Services never read req or res.
  • One error type (AppError(status, code, message)) and one error middleware that returns { error: { code, message } }.
  • KYC files are private in S3, uploaded via pre-signed URLs and read through 5-minute signed links. Only the last 4 digits of Aadhaar are kept.
  • Webhooks are verified with an HMAC signature and processed once, keyed by event id.

Booking state machine

PENDING_PAYMENT→ CONFIRMED→ ONGOING→ COMPLETED→ DEPOSIT_SETTLED

Side exits: EXPIRED (hold not paid within 15 min) · CANCELLED (by customer or admin, refund by policy) · EXTENDED (new end time, re-checked against the exclusion constraint). Transitions are defined in booking.state.ts; any transition not listed there throws 409 INVALID_TRANSITION.
